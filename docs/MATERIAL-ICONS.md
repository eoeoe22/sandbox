# 물질 아이콘 · 패턴

> **상태: 자동 유도 + 손그림 덮어쓰기 계층 구현 완료** (`src/game/render/materialSvg.ts`).
> 팔레트 126종 중 **100종이 캔버스와 같은 패턴을 유도하고**, **28종은 칩을 손그림으로
> 덮으며**(둘은 겹친다 — 손그림 28종 중 7종은 아래에 패턴이 이미 있다), **아직 칩이 단색인
> 건 5종**이다. §7이 그 5종을 정리한다(그리는 쪽 규격은 저장소 없이 넘길 수 있는 별도
> 브리프). 저작 지침은
> [`.claude/skills/create-svg-assets/SKILL.md`](../.claude/skills/create-svg-assets/SKILL.md) §7.

## 0. 문제

오브젝트는 팔레트 칩이 **인월드 스프라이트 그대로**라 직관적이다
(`objectSvgFor` → `MaterialPalette.svelte`). 반면 이 게임의 주 구성요소인 물질은
**전부 18×18 단색 사각형**이었다 — 실제 캔버스에서는 모래가 알갱이마다 밝기가 다르고,
메시는 격자로 짜여 있고, 컨베이어는 화살표가 흐르고, 용암은 온도로 달아오르는데,
팔레트에서는 그 정보가 하나도 보이지 않았다.

이미 렌더러가 물질별로 **9가지 질감·패턴 계통**을 그리고 있다. 새 아트를 지어내는
게 아니라 **이미 그리고 있는 것을 아이콘에 되비추는 것**이 이 작업의 본체였다.

## 1. 원칙

1. **아이콘은 캔버스의 축소판이다.** 눈대중 근사 금지 — 렌더러가 쓰는 공식과
   타일 수식을 그대로 재생한다.
2. **자동 유도가 기본, 전용 아트는 예외.** 물질 파일에 아무것도 안 써도
   `phase` / `colorVary` / 패턴 플래그만으로 올바른 아이콘이 나온다.
3. **결정론.** 아이콘 생성에 `Math.random()` 금지. 같은 물질 칩이 플라이아웃과
   검색 결과에서 달라 보이면 안 된다. (`test/materialicons.ts`가 파일 첫 줄에서
   `Math.random`을 throw로 바꿔 이걸 강제한다.)
4. **읽히는 크기에서 픽셀이 깨지지 않아야 한다** — §3의 `N = 9` 참고.

## 2. 구조

### 2.1 그려지는 곳

|---|---|---|---|

| `starChip` 스니펫(즐겨찾기·검색 결과) | `components/MaterialPalette.svelte` | 18×18 | 패턴 |
| 블렌드 브러시 피커 트리거 | `components/MaterialPicker.svelte` | 16×16 | 패턴 |

**돋보기 11×11은 의도적으로 제외**한다. 18px에서 읽히는 패턴이 11px에서는 진흙이
되고, 돋보기 행에는 물질 이름이 이미 나란히 붙어 있어 스와치가 식별을 떠맡지 않는다.

### 2.2 재생하는 수식

`materialSvg.ts`의 `patchFor()`는 `CanvasRenderer.render()`의 배타적 분기 사슬을
**같은 순서로** 복제한다. 순서가 핵심이다 — Fan은 `lattice` **이면서** `windArrow`,
Diamond는 `lattice` **이면서** `checker2x2`, Solar Panel은 `lattice` **이면서**
`solarPattern`, Wall은 `lattice` **이면서** `brickPattern`, Woofer는 `lattice` **이면서**
`wooferPattern`이라, 먼저 걸리는 분기만 그린다. 그런 물질의 `lattice`는 **두 번째 톤을
공급하는 역할일 뿐**이다. 순서를 바꾸면
전기 탭 절반이 조용히 체커보드가 된다 — `test/materialicons.ts`의 골든 타일 10종이 이걸
잡는다.

| 계통 | 수식 |
|---|---|
| 밝기 틴트 | `d = ((src - 128) * amp) >> 7`, 채널별 가산 후 클램프 |
| 진폭 `amp` | `colorVary ?? (glow ? 0 : petroleum ? 7 : Powder ? 18 : Liquid ? 22 : 0)` |
| `lattice` | `(x ^ y) & 1` |
| `checker2x2` | `((x >> 1) ^ (y >> 1)) & 1` + 틴트 |
| `batteryPattern` | 4×5 타일: `px===1&&(py===1\|\|py===2) \|\| px===2&&(py===2\|\|py===3)`, 패턴 픽셀 `0xff000000` |
| `solarPattern` | `x % 4 === 3 \|\| y % 6 === 5` |
| `brickPattern` | 6×4 타일, 홀수 켜만 3칸 밀림: 줄눈 `y%4===3 \|\| (x + (켜&1 ? 3 : 0)) % 6 === 5`, 벽돌 윗줄 `y%4===0`은 `tinted(base, +40)` |
| `wooferPattern` | 9칸 타일, 배가된 좌표 `ax = 2*(x%9) - 8`의 제곱거리 `d2 = ax²+ay²`로 반경 판정: 캡 `d2≤4` = `tinted(base,−29)`, 콘 `≤25` = `lattice`, 림 `≤49` = `tinted(base,−20)`, 그 밖은 배플(base) |
| `arrow` / `windArrow` | 주기 4 텐트 `fold = y&2 ? 3-(y&3) : y&3` |
| `triArrow` | 8×5 타일, 레인 1~6이 1,2,3,3,2,1칸 |
| `coilPattern` / `stripePattern` | `y&3 ∈ {1,2}` / `x%3===1` |
| `glow` | `shade()`가 `cool → color`로 선형 보간 |

**공유 구현**: `tinted` / `frosted` / `buildGlow` / `shade`와 `GlowRamp`를
`CanvasRenderer`의 private static에서 **`render/color.ts`로 올렸다.** 렌더러와 아이콘
생성기가 한 구현을 쓰므로, 한쪽만 손보다 어긋나는 일이 구조적으로 불가능하다.
`spriteRects` / `pixelSvg`도 `objectSvg.ts`에서 `render/spriteSvg.ts`로 옮겨 공유한다.

### 2.3 아이콘이 읽을 수 없는 것 — 그리고 대신 하는 것

**틴트 필드.** `Grid.tint`(가루: 셀당 1바이트, 생성 시 심고 이동 시 따라감)와
`Grid.bgTint`(액체: 위치 기반 필드)는 **월드 상태**라 팔레트에서 접근할 수 없다.
아이콘은 `(id, x, y)`의 **순수 해시**로 바이트를 합성해 **같은 공식에** 넣는다.

그런데 두 필드의 분포가 다르다. 가루의 틴트는 `(Math.random()*256)|0`으로 심겨
**균등분포(σ ≈ 73.6)** 지만, 액체가 읽는 배경 필드는 OU 드리프트가 붙어 있어
정상상태 분산이 `300 / (1 − 0.88²) ≈ 1330`, 즉 **σ ≈ 36.5로 절반**이다. 실제로
물웅덩이는 `LIQUID_VARY 22`가 시사하는 것보다 눈에 띄게 덜 일렁인다 —
`POWDER_VARY 18`보다 진폭이 큰데도 그렇다. 아이콘은 해시 3개를 더해 정규분포를 근사한
뒤 이 σ에 맞춘다(`BG_SIGMA_SCALE`). 검사가 이 역전(`water < sand`)을 핀으로 박아 둔다.

**플레이 중에만 있는 셀 상태.** 장치의 전원 카운트다운, glow 물질의 실시간 온도,
Seed의 발아 진행도. 아이콘은 **칠했을 때 나오는 상태**를 보여준다 — 전원 꺼짐,
`PointerPainter`가 찍는 기본 방향(컨베이어 오른쪽, Fan/Laser/성형작약 `FAN_RIGHT`).
범위를 보여주는 게 요점인 두 경우(glow 램프, Seed)만 예외다.

**의도적 미재생**: `Material.freeze` 서리. 팔레트는 항상 따뜻한 상태를 보여준다.

## 3. 구현 결정

**`N = 9` (9×9 패치).** 실제로 그려지는 크기에서 셀이 정수 디바이스 픽셀에 떨어지는
값이다: 팔레트 스와치 18 CSS px → DPR 1에서 정확히 2px, DPR 2에서 4px. 12는 DPR 1에서
네 행마다 한 행이 사라지고, 8은 DPR 2에서 깨진다. 동시에 모든 패턴을 담기에 충분하다 —
lattice 4.5주기, 배터리 타일 약 2개, 컨베이어 셰브런 2개, 태양광 셀 하나와 이음매,
스페클 81알. 16px인 피커 트리거만 9로 나누어떨어지지 않으므로 거기만
`shape-rendering: auto`로 부드럽게 리샘플한다(행이 날아가는 것보다 낫다).

**색상별 `<path>`, 런별 `<rect>` 아님.** 스프라이트 아트에서는 둘이 비슷하지만, 밀집
스페클에서는 아니다 — 81셀 × 약 36색은 병합할 런이 거의 없어서, rect는 속성 이름을
81번 반복하고 path는 색을 한 번만 적고 셀당 12자만 쓴다. 팔레트 **검색 뷰에 가상
스크롤이 없어** 126개가 동시에 살아 있을 수 있으므로 이 차이가 실측으로 컸다:
실측 **340,942 B → 166,368 B**(333 KB → 162 KB), 구름 도입 후 168,555 B.

**타일 전체 배경 rect + 편차 셀만.** `spritePaths`가 0을 건너뛰므로, 최빈색을 전체
타일 rect로 한 번 깔고 나머지만 그린다. 평면 물질은 **shape 1개(237 B)**, 배터리·코일·
태양광은 패턴 셀 값만 낸다.

**실측치** (126종): 합계 **188 KB**(손그림 배선 전 164 KB, 손그림 13종 시점 176 KB),
중앙값 1.7 KB, 최대 **3.4 KB**(3,386 B — Nanobot의 군체 스웜, Nuke Waste의 3,156 B를
넘어섰다). 가장 싼 쪽은 평면 물질의 **237 B**(shape 1개), 구름 기체가 593 B, 손그림은
354~3,386 B다. 검사가 개별 4 KB·합계 250 KB를 상한으로 잡고 있다 — 손그림 최대치가 상한에
가장 가까운 값이므로, 군체형 아이콘을 더 늘릴 땐 rect 수를 먼저 볼 것.

**손그림이 유도 타일보다 반드시 비싼 건 아니다.** 2순위 15종의 하위 절반은 유도 스페클보다
싸다 — Mercury·Liquid Gallium이 **354 B**로 전체에서 가장 싼 손그림이고(수평 반사선 두 줄이
rect 3개다), Iron 466 B, Aluminum 524 B, Heatpipe 579 B가 그 뒤다. 비싼 건 형태가 많은
쪽이다: Coal 2,081 B(덩어리 셋), Turbine 1,760 B(날개 넷). 브리프의 상한이 rect 100개인데
하네스의 4 KB는 **약 65개**에서 걸리므로, 발주에는 **60개**로 못 박아 넘긴다.

이 절의 바이트 수는 전부 **출하 마크업 전체**(`materialSvgFor()`가 돌려주는 문자열,
`<svg>` 래퍼 포함)다. `scripts/check-icon-svg.mjs`가 찍는 "출하 N B"는 래퍼를 뺀 **rect
나열만**이라 손그림당 약 180 B 작다(예: mercury 170 B / 354 B, nanobot 3,202 B / 3,386 B).
두 수를 한 줄에 섞어 적지 말 것 — 실제로 한 번 섞어 적었다.

**메모이제이션은 모듈 스코프.** `MaterialPalette`의 `categories`/`matches`는
`$derived.by`라 **로케일이 바뀌거나 검색어를 한 글자 칠 때마다 재실행**된다.
컴포넌트 안에서 계산하면 126개가 매번 다시 만들어진다.

**기각한 대안**

- **CSS `background-image` / 그라디언트**: 픽셀 단위 노이즈도, battery의 4×5 계단도
  표현할 수 없다.
- **칩마다 `<canvas>`**: 팔레트에 **DPR 처리가 전혀 없다**(`devicePixelRatio`를 읽는
  곳은 `Game.ts` 한 곳뿐). 검색 결과에 캔버스 126개가 뜨고 `$derived.by` 재실행마다
  재생성된다.
- **`<defs>` / `<linearGradient>` / `id`**: 이 문자열들은 `{@html}`로 주입되고 **같은
  문자열이 한 문서에 여러 번 살아 있을 수 있다**(플라이아웃 + 즐겨찾기 + 검색 결과).
  문서 스코프 이름은 자기 복제본과 충돌한다. 검사가 `id=` / `<defs` / `<style` /
  `url(` 출현을 금지한다.

|---|---|---|---|
| **B1. 틴트 노이즈 가루** (amp 18) | 28 | 합성 해시 + 밝기 오프셋 | ✅ |
| **B1b. 틴트 노이즈, 커스텀 amp** | 7 | 같은 처리, amp는 `colorVary` (Obsidian 6 … Termite/Nanobot 22) | ✅ |
| **B2. 액체 배경 노이즈** (amp 22) | 14 | 같은 수식, OU 정상상태 σ에 맞춘 좁은 분포 | ✅ |

| **B5. 평면 기체** (amp 0) | 15 | 꽉 채운 구름 실루엣(18셀 그리드) | ✅ |

| **B7. glow 온도 램프** | 16 | 램프 상위 55%를 세로로, 셀별 지터로 얼룩 | ✅ |
| **B8. 엔진 기존 패턴** | 14 | 타일 수식 1:1 재생 | ✅ |

합 = 126. **패턴이 붙은 것 100종, 자동 유도로는 단색인 것 26종**(B4 24 + B6 2).
이 위에 **손그림 28종**이 얹힌다(§4.1). 그중 **21종은 아래 타일이 단색**이고(B4 19 +
B6 2), 나머지 7종은 **이미 패턴이 있는데도** 손그림으로 덮은 것이다 — Fire·Blue Flame(B5
구름), Solar Panel(B8 셀 격자), Wall(B8 벽돌), Woofer(B8 드라이버 격자), Antimatter(B1
스페클), Nanobot(B1b 스페클). 패턴이 있어도 그 패턴이 물질을 설명하지 못하기 때문이다.
따라서 **아직 칩이 단색인 건 5종**(26 − 21)이고, 그게 §7.1에 남은 목록이다.

**버킷 수는 손그림이 늘어도 변하지 않는다.** 버킷은 *유도 타일*의 분류이고 손그림은 칩만
덮으므로, Iron은 손그림을 받은 뒤에도 여전히 B4(평면 고체)다 — `generatedSvgFor()`가 그
단색 타일을 계속 만들고 검사도 계속 그걸 본다(§6의 "Stone·Iron·Mercury·Liquid Gallium은
단색으로 그려진다" 항목이 손그림 28종 시점에도 그대로 통과하는 이유다). 지금까지 버킷을
실제로 옮긴 건 Wall 하나뿐이다: 벽돌 패턴이 **캔버스에** 붙으면서 B4 → B8로 갔다(단색
27 → 26). Woofer는 `lattice` 위빙을 이미 갖고 있어 처음부터 B8이었고, 드라이버 격자로
바뀐 것은 **같은 버킷 안에서의 교체**다.

**기체가 구름인 이유 — 그리고 디졸브를 버린 이유.** 기체 셀은 인월드에서 평면 한 색이
맞지만, 꽉 찬 사각형은 **같은 색 고체와 구별되지 않는다**. 이 기능이 존재하는 이유가
바로 그거다. 첫 구현은 셀을 흩뿌렸다(위는 빽빽하고 아래로 갈수록 성기게 — 실제 플레이
장면에 가까운 쪽). 실기 확인 결과 **모양이 아니라 손상으로 읽혔다** — 의도한 실루엣이
아니라 무작위로 뚫린 구멍. 그래서 발상은 남기고(기체는 판 위에 뜬 증기 덩어리이지
벽돌이 아니다) 실행만 바꿨다: **꽉 채운 구름 한 덩이**, 주변은 판 자체의 배경색.

구름은 **18셀 그리드**를 쓴다. 격자나 셰브런은 9셀로 충분하지만 곡선은 아니고, 9×9
구름은 그냥 덩어리다. 18은 9를 고른 이유였던 픽셀 정렬을 그대로 지킨다 — 18 CSS px
스와치에서 셀당 정확히 1 device px(DPR 1) / 2(DPR 2). 두 색뿐이라 런 병합이 잘 먹어서,
셀이 4배인데도 9×9 스페클보다 마크업이 **작다**(593 B).

구름 실루엣은 원 합집합으로 생성하지 않고 **ASCII로 직접 적어 뒀다**(`GAS_CLOUD`).
출하되는 그림이 곧 누군가 읽고 승인한 그림이 되고, 검사가 그대로 골든으로 박을 수 있다.

### 4.1 손그림 덮어쓰기 계층

손그림은 **28종**이고, 있는 이유가 서로 반대인 두 갈래다.

**(가) 개념이 정체성인 것 — 13종.** Void의 "삭제"나 Clone의 "복제"는 색도 질감도 아니라서,
렌더러가 재생할 패턴 자체가 존재하지 않는다:

Void · Clone · Antimatter · Virus · Nanobot · Catalyst · Amber · Aerogel · Wall ·
Fire · Blue Flame · Solar Panel · Woofer

**(나) 인월드에서 정직하게 한 색인 것 — 15종.** 철판은 실제로 화면에서 한 톤이므로
**되비출 패턴이 없다.** 그래서 칩이 이 계층이 생긴 뒤에도 맨 사각형으로 남아 있었고,
손그림이 그 표면에 결·면·광택을 **처음으로** 넣는 유일한 자리다:

Wood · Coal · Ice · Glass · Dry Ice · TNT · Cluster · Napalm · Iron · Aluminum ·
Gallium · Heatpipe · Turbine · Mercury · Liquid Gallium

**(가) 중 일곱은 자동 유도가 이미 뭔가를 그리고 있었는데도 덮었다.** Fire·Blue Flame·
Antimatter·Nanobot은 패턴이 나오긴 하지만(구름·스페클) 그게 "불"이나 "쌍소멸"을
설명하지 못한다. Solar Panel·Wall·Woofer만 이유가 다르다 — Solar Panel은 **4×6 셀 타일이
9셀 창에 온전히 안 들어가** 위아래 셀 높이가 어긋나는 생성기 쪽 한계이고, Wall과 Woofer는
반대로 **손그림이 먼저 있었고 그 패턴을 캔버스로 옮긴** 경우다(아래 참고).

**Blue Flame은 Fire의 팔레트 스왑이다.** 같은 불꽃 실루엣에 색만 파랑 계열로 바꿔
얹었다(`#ff7828`→`#5aa0ff`, 심지 `#ffc24a`→`#c8ecff`, 잘라낸 바깥 `#3a1509`→`#0a1836`).
기하는 한 칸도 건드리지 않았고, 옮길 때 색 대응표를 스크립트로 돌려 미대응 색이 하나라도
있으면 실패하게 했다 — 손으로 4색을 찾아 바꾸다 한 군데를 놓치면 주황 얼룩이 남는다.
둘이 형제 물질이라(같은 `category: 'fire'`, 같은 거동에 온도만 다름) 실루엣을 공유하는
게 오히려 맞다.

**Wall — 칩의 패턴을 캔버스로 되돌린 경우.** 나머지 열한 종은 "칸반이 설명 못 하는 걸
칩에서만 보완"하는 방향인데, Wall은 그 방향이 뒤집혔다. 손그림이 이미 줄쌓기 벽돌
(running bond)이었고, 그게 인월드에서도 성립하는 패턴이라 `Material.brickPattern`으로
렌더러에 넣었다(§2.2 수식표). 타일은 6×4로, 줄눈이 벽돌의 오른쪽·아래 한 칸이고 홀수
켜가 반 장(3칸) 밀린다.

옮긴 것은 **구조 세 가지**(줄쌓기·줄눈·윗줄 하이라이트)이고 **치수는 아니다.** 아이콘의
벽돌이 11×11(줄눈 2칸)로 거의 정사각인 건 24셀 타일에 2:1 벽돌 두 장이 나란히 안 들어가기
때문일 뿐이다. 월드 격자에는 그 제약이 없으니 5×3으로 벽돌답게 뒀다 — 4×4는 벽돌이 아니라
타일로 읽힌다. 주기를 작게 잡은 이유는 `SOLAR_CELL_W`가 원화의 4×7을 3×5로 줄인 것과 같다:
패턴은 **월드 셀 단위로 그려지므로** 주기가 크면 벽을 스무 칸쯤 그려야 무늬가 보이기
시작한다. 6×4면 열두 칸 벽에서 이미 벽돌 두 장과 그 아래 엇갈린 켜가 나온다.

두 톤 모두 아이콘에서 그대로 가져왔다: 줄눈은 `lattice: #484c52`, 벽돌 윗줄은
`tinted(base, +40)` — `#787c82`에서 정확히 `#a0a4aa`가 나오는 값이라 캔버스와 칩이 같은
방향으로 빛을 받는다. Wall은 `latticeFilter`가 아니므로 `lattice`를 준 것이 통과
거동을 바꾸지 않는다(§`SimContext.canOverlapAt` — 필터는 옵트인이다).

**Woofer — Wall과 같은 방향, 다만 원판이 원이 아니었다.** 넘겨받은 그림은 24셀 타일 한가운데
스피커 드라이버 한 개다(림 `#16161c` / 콘 `#3f3f4a` / 더스트캡 `#0d0d12`, 배플 `#2a2a32`).
**그대로는 검수를 통과하지 못했다** — 지름 18칸 원판이라 기본색이 52%밖에 안 남아 60% 규칙에
걸렸다(칠한 칸 276 > 상한 230). 1차로는 바깥 림 한 겹을 깎아(2칸 → 1칸) 61%를 만들어 넘겼다.

**그 결과가 "너무 사각형"이라는 지적을 받았고, 원인은 림 두께가 아니라 실루엣이었다.**
줄별 폭을 세 보면 8 · 12 · 14 · 16 이고 그 뒤로 **16칸이 여덟 줄 내리 이어진다** — 모서리만
깎은 사각형이다. 지름 16 원의 정직한 래스터는 6 · 10 · 12 · 14 · 14 · 16 이라 평평한 변이
여덟 줄에서 **여섯 줄로 줄고**, 극단 줄이 8칸에서 6칸으로 좁아진다. 그래서 원판을 수식으로
다시 깔았다(중심 11.5, 반경 8, 캡 반경 4 · 콘 반경 6.5의 동심 밴드).

**다시 깔고 나니 규격 문제도 같이 없어졌다.** 원 면적은 208칸이라 상한 230 안에 들어오고
기본색이 **63.9%** 남는다. 남은 여유로 **유저가 원래 그린 2칸 림을 복원했다**(콘 반경 6.5는
적도에서 림이 정확히 2칸이 되는 값이다). 캡은 애초에 손댈 필요가 없었다 — 원본 캡이 이미
반경 4의 정직한 원 래스터였고, 새로 깐 것과 **칸 단위로 동일하다.**

캔버스 쪽은 `Material.wooferPattern`이다. 9칸 타일마다 드라이버 하나(지름 7칸 + 배플 2칸)를
같은 세 밴드로 그린다. **주기는 8이었고 드라이버가 6칸이었다.** 둘 다 정직한 원 래스터지만
**짝수 지름에는 중심 줄이 없어서** 폭이 4/6/6/6/6/4로 나온다 — 여섯 줄 중 넷이 최대폭이라
육각형으로 읽힌다. 7칸에서는 3/5/7/7/7/5/3이라 평평한 줄이 셋뿐이고 극쪽으로 두 단씩 좁아진다.
칩이 사각형으로 읽힌 것과 **같은 원인이라 같이 고쳤다.**

비율은 이제 정확히 겹치지 않는다: 칩의 드라이버는 24셀 타일의 0.67(16/24)이고 여기서는
0.78(7/9)이다. 림도 칩은 2칸, 여기는 1칸이다 — 7칸 안에서 림을 두 겹 두르면 콘이 남지 않는다.
(옛 문단은 칩 비율을 0.75라고 적어 6/8과 "정확히 같다"고 했는데, 16/24는 0.67이다. 산수가
틀렸던 것이고 지금은 두 값을 그대로 적어 둔다.)

반경 판정은 **배가된 좌표의 제곱거리**로 한다: `ax = 2*(x%9) - 8`로 타일 중심을 0에 놓으면
주기가 짝수든 홀수든 중심이 정수로 떨어지고, `d2 = ax²+ay²`를 제곱한 반경과 비교하므로 sqrt도
룩업 테이블도 없다.

**네 톤 중 셋만 정확하다.** 물질이 가질 수 있는 두 번째 색은 하나(`lattice`)뿐이라, 그걸 콘에
주고 림·캡은 `tinted(base, −20)` / `tinted(base, −29)`로 만든다. 칩의 램프가 파란쪽으로 아주
약간 기울어 있어서(림이 `#16161c`인데 base−20은 `#16161e`) 두 톤이 청색 채널에서 2~3단 어긋난다
— 거의 검정인 색에서 보이는 단차 아래다. 네 톤을 다 정확히 맞추려면 오프셋이 아니라 색 목록이
필요하다.

**물질 기본색도 그림에 맞췄다.** Woofer의 등록색은 `#282a30`이었고 그림의 배플은 `#2a2a32`다
(적·청 2단 차이). 검사가 "손그림은 그 물질의 등록색으로 시작해야 한다"를 요구하므로 둘 중
하나는 양보해야 했고, 그림을 고치는 대신 물질 쪽을 옮겼다 — 그래야 캔버스와 칩이 **한 기본색**을
공유한다. 옛 구리색 `lattice` 위빙(그릴 무늬)은 드라이버가 대체했다.

**Virus·Nanobot — 한 마리에서 군체로.** 첫 판은 둘 다 **타일 하나를 채운 개체 한 마리**
였는데, 이 둘의 정체성은 "번진다 / 번식한다"이므로 개체가 아니라 **무리**로 읽혀야 한다.
다시 그릴 때 24×24를 직접 찍지 않고 **12×12 굵은 격자**(굵은 칸 하나 = 2×2 셀) 위에
모티프를 배치했다 — 브리프의 "최소 두께 2칸"이 구성상 자동으로 성립하고, 브리프의
**형태 간 2칸 간격 규칙도 5×5 상자 검사로 기계 확인**할 수 있다(굵은 격자에서 체비쇼프
2칸 = 셀 3칸 = 규칙 통과). 바이러스는 5×5 모티프의 가시 달린 구체 넷을 최소 간격까지
붙여 채우고, 나노봇은 3×3 모티프의 기계 진드기 여덟을 **두 방향으로 번갈아** 엇갈리게
놓았다. 방향을 섞은 건, 같은 글리프를 규칙적인 피치로 깔면 무리가 아니라 **벽지로
읽히기** 때문이다(실제로 첫 재시도가 그렇게 나왔다).

**Obsidian — 패턴이 아니라 진폭.** 흑요석은 손그림을 받지 않았다. 화산 *유리*라서 필요한
건 무늬가 아니라 **더 매끈한 면**이었고, `colorVary`를 14 → 6으로 좁혔다. 기본색이
`rgb(48, 36, 68)`로 거의 검정이라 채널값이 36~68 사이에 있고, 같은 진폭이 중간 톤 물질에
비해 훨씬 크게 읽힌다 — 14에서는 유리가 아니라 거친 노이즈였다. 진폭은
`varyAmplitude()` 하나를 캔버스와 아이콘이 같이 읽으므로 **이 숫자 하나가 양쪽을 동시에
좁힌다**. Diamond의 "낮은 다이나믹 레인지"(10)보다도 아래라는 걸 검사가 핀으로 박아 둔다.

### 2순위 15종 — 병렬 발주에서 실제로 무엇이 깨졌나

평면 한 색인 15종(위 (나))은 **물질마다 에이전트 하나**로 병렬 발주하고, 그 결과를 **작성자
의도를 모르는 검수 에이전트**가 격자만 보고 다시 판정하게 했다. 1차에서 **15장 전부가 규격
검수(`check-icon-svg.mjs`)를 통과**했는데 **그중 9장이 물질로 읽히지 않았다.** 규격과 가독성이
서로 다른 축이라는 게 이 라운드의 핵심 교훈이다.

**깨진 방식이 거의 한 가지였다: 타일을 무늬로 덮으려 한 것.** 여기서 기본색 칸은 배경이
아니라 **물질 자체**다(캔버스에서 나무 칸은 화면을 나무로 채운다). 그래서 칠이 타일 변에
닿는 건 정상인데, **같은 모티프를 규칙적인 간격으로 되풀이하면** 표면이 아니라 벽지가 된다.
1차 실패의 대부분이 그것이었다 — Wood는 결이 정확히 11줄 주기로 반복됐고(y=13~16이 y=2~5와
바이트 단위로 동일), TNT는 칠한 띠 다섯 개 중 셋이 복제였고, Aluminum은 **24줄이 전부
같았다**(세로 줄무늬 필드). 나머지는 눈으로만 잡히는 것들이었다: Ice는 모서리에서 모서리로
가는 사선 하나, Dry Ice는 드롭섀도 붙은 흰 UI 카드, Iron은 UI 구분선 두 개, Heatpipe는
검은 테로 막힌 상자, Napalm은 광택이 덩어리에서 떨어져 나온 검은 얼룩.

**벽지를 기계로 세는 도구를 만들어 2차 발주에 함께 넘겼다**(세로 런렝스로 띠를 묶고, 같은
프로필이 세 번 이상 나오거나 복제 쌍이 같은 간격을 공유하는지 + 1칸 고립 칸 + 연결요소 간
체비쇼프 간격). 그게 Wood·TNT·Cluster·Aluminum을 잡았다.

**다만 그 도구는 게이트가 될 수 없다 — 저장소에 넣지 않았다.** 이미 출하된 28장에 돌려 보니
멀쩡한 그림이 대량으로 걸렸다. 사유가 둘 다 정당했다: **미러 대칭**(우퍼의 동심원은 아래
절반이 위 절반의 복제일 수밖에 없다)과 **의도된 주기**(태양광 셀 격자는 반복 자체가 그
물질이다). 대칭 접기와 "세 번 이상" 조건으로 우퍼·반물질은 통과시켰지만, 태양광·나노봇·
앰버·촉매는 여전히 걸리고 **가로 전폭 띠 하나가 모든 열을 "칠한 열"로 만들어** 빈 열끼리
복제로 잡히는 인공물도 남았다. 그래서 이건 **판정 보조**이지 규칙이 아니다 — 걸린 것을
사람이 격자로 확인하는 용도다. 규격 게이트는 `check-icon-svg.mjs` 하나로 남는다.

**2차에서도 안 된 넷은 직접 그렸다.** TNT(포장 밴드를 두른 장약 블록), Wood(굽은 모양이
서로 다른 결 세 줄 + 옹이), Cluster(엇갈려 놓인 자탄 세 발)는 ASCII 격자를 손으로 짜서
구웠다. Gallium은 한 칸만 고쳤다 — 왼쪽 윤곽과 아래 윤곽이 **대각으로만** 맞닿아 있어서,
0.75배로 줄면 그 모서리가 이가 빠진다.

**계층은 얇은 뚜껑이다.** `generatedSvgFor()`는 예전 본체 그대로이고,
`materialSvgFor()`가 손그림을 먼저 보고 없으면 그리로 떨어진다. 물질 정의는 손대지
않는다 — `.svg` 한 장을 넣고 모듈을 다시 굽는 것이 배선의 전부다.

**두 함수를 나눈 건 장식이 아니다.** Solar Panel은 골든 타일이고, 그 골든이 지키는
`solarPattern` 분기는 칩을 손그림이 가져간 뒤에도 살아 있다. 그래서 골든은
`generatedSvgFor()`를 직접 보고, 검사가 "손그림이 칩을 덮었는데 아래 타일은 여전히
유도된다"를 따로 확인한다.

**`.svg`는 런타임에 로드되지 않는다.** 오브젝트 스프라이트와 같은 규칙이다 —
`scripts/build-hand-icons.mjs`가 `src/game/render/handIcons.ts`로 굽는다. Vite의
`?raw`·`import.meta.glob`이 더 간단하지만 **테스트 하네스를 깨뜨린다**(esbuild로 직접
번들해 Vite 변환이 없다). `.svg`만 고치고 다시 굽지 않으면 **옛 그림이 조용히 계속
나가므로**, `npm run check:hand-icons`를 빌드 단계에 물려 두었다.

파싱은 `scripts/icon-svg.mjs` 한 곳뿐이다. 검수기와 배선 생성기가 파일을 다르게 읽으면
**검수는 통과했는데 배선은 다르게 그리는** 상태가 되기 때문이다.

**Seed.** `auxPalette`(발아 진행 램프, 갈색→녹색)를 쓰는 유일한 팔레트 물질이라 "맞는
단색"이 없다. 진행도를 **제곱으로 눌러** 아래 2/3는 실제로 칠리는 휴면 갈색으로 두고
맨 위만 녹색으로 틔운다 — 싹 난 씨앗.

## 5. 남은 것

1. **손그림 5종** — §7.1의 나머지(Stone · C4 · Fuse · Asphalt · Rust). 들어오는 대로
   `temp/material-icons/`에 넣고 `npm run build:hand-icons`만 돌리면 붙는다.
2. **브라우저 실측 미확인.** 검색 결과 최악 케이스(동시 126칩, 가상 스크롤 없음)의
   체감 비용은 아직 측정하지 않았다. 마크업 총량은 §3의 실측치로 잡혀 있다.

## 6. 검증

`npm run test:materialicons` (`test/materialicons.ts`). 지키는 것:

- **결정론** — 파일 첫 줄에서 `Math.random`을 throw로 교체.
- **분기 순서** — 10개 패턴 계통의 골든 타일 ASCII. 사슬을 재정렬하면 그림이 바뀐다.
  Wall의 벽돌 골든은 **켜가 엇갈리는지**까지 본다 — 줄눈이 세로로 일렬이 되면 벽이 아니라
  격자이므로, `BRICK_OFFSET`이 사라지면 그림이 바뀐다. 골든의 글자는 기본색 `.`, 패턴 톤이
  하나면 `o`, 둘이면 밝은 쪽 `i`·어두운 쪽 `o`다(패턴 톤끼리의 상대 밝기로 매긴다 —
  기본색과 비교하면 태양광 이음매처럼 기본색보다 **밝은** 패턴에서 글자가 뒤집힌다).
- **마크업 안전성** — `id=` / `<defs` / `<style` / `url(` / `<script` / `<image` 금지,
  전 타일이 빈 셀 없이 채워지는지(칩 배경이 비쳐 선택 시 색이 변하면 안 됨).
- **평면은 평면으로, 질감은 질감으로** — Stone/Iron/Mercury/Liquid Gallium은 톤 1개,
  Sand/Water/Crude Oil/Diamond는 8톤 초과. (이 검사들은 손그림 계층을 지나쳐
  `generatedSvgFor()`를 직접 본다.) Wall은 벽돌 패턴이 붙으면서 이 목록에서 빠졌다 —
  이제 골든 쪽이 지킨다.
- **틴트가 진폭을 넘지 않음**, **액체가 가루보다 덜 일렁임**(§2.3의 역전),
  **Obsidian이 틴트 물질 중 가장 좁음**(Diamond의 10보다 아래 + 타일의 밝기 폭 12단 이내).
- **glow는 위가 뜨거운 램프**, **기체는 구멍 없는 구름 골든**(+ glow를 가진 기체인
  Blast는 여전히 glow 분기로 가는지), **Fireworks 3색**,
  **Seed는 위가 녹색**.
- **손그림 덮어쓰기 계층** — 손그림이 있는 물질에서만 오버라이드가 이기고 나머지는
  유도 타일 그대로인지, 아이콘 파일명이 **실재하는 물질을 가리키는지**(안 그러면 조용히
  안 그려진다 — 빌드에서도 잡지만 여기서 한 번 더 본다), 각 손그림이 **그 물질의 등록
  색으로 시작하는지**, 그리고 Solar Panel이
  칩을 손그림에 넘긴 뒤에도 `solarPattern` 유도 타일이 살아 있는지.
- **크기 예산** — 개별 4 KB, 합계 250 KB.

`npm run check:hand-icons` (`npm run build`에 물려 있음). **신호 없이 실패하는 것들**만
모아 잡는다 — `.svg`만 고치고 다시 굽지 않아 옛 그림이 계속 나가는 경우, 파일명이 어떤
물질의 아이콘 키도 아니라 모듈에는 실리는데 화면에는 안 나오는 경우, 하위 폴더나 대문자
확장자라 아예 읽히지도 않는 경우.

파일명 검사는 패턴이 아니라 **실제 물질 목록과 대조**한다(`check-material-ids.mjs`의
정적 스캔을 공유). 단순 kebab 정규식으로 두면 `liquid-n₂` 같은 정상 키를 거부한다.

## 7. 전용 SVG 규격 (외부 저작)

손그림이 필요한 건 세 부류다. **28종은 그려서 배선까지 끝났고**(§4.1), **5종이
남았다**.

1. **인월드에서도 평면 한 색인 것 26종** — §4의 B4(평면 고체 24) + B6(수은·액체
   갈륨). 생성기가 재생할 패턴 자체가 없다.
2. **정체성이 색도 질감도 아니라 개념인 것**(Void, Clone, Virus, Antimatter…) —
   패턴이 이미 붙어 있어도 그 패턴이 물질을 설명하지 못한다. 대부분 1번과 겹치고,
   겹치지 않는 건 Fire·Blue Flame·Antimatter·Nanobot 4종이다(넷 다 지금 패턴이 있다).
3. **자동 유도 결과가 실기에서 어색하다고 판정된 것** — 태양광 패널 하나. 4×6
   타일이 9셀 창에 온전히 안 들어가 위아래 셀 높이가 어긋난다.
4. **손그림이 먼저 있고 그 패턴을 캔버스로 되돌린 것** — Wall(줄쌓기 벽돌)과
   Woofer(드라이버 격자). 위 세 부류와 방향이 반대라, 발주 목록이 아니라 §4.1의 기록이다.

발주 당시엔 1번이 27종이라 27 + 3 + 1 = 31이었다. 그 뒤 Wall이 벽돌 패턴을 받아 1번에서
빠지고(§4.1), Blue Flame이 2번에 들어왔다 — 26 + 4 + 1 = 31로 총량은 그대로다. 1순위가
3번과 2번을 전부 소화했고 2순위가 1번의 15종을 소화했으므로, **남은 5종은 전부 1번(평면
한 색)** 이다. Woofer는 애초에 어느 발주에도 없었다(이미 `lattice` 위빙이 있었다) — 4번으로
뒤늦게 합류했을 뿐이다.

**그리는 쪽 규격은
[`.claude/skills/create-svg-assets/MATERIAL-ICON-BRIEF.md`](../.claude/skills/create-svg-assets/MATERIAL-ICON-BRIEF.md)
에 있다** — 작업 절차·파일 형식·금지 목록·그리기 규격·점검표를 인라인해 둔 자체 완결
문서다. 상정 소비자는 **저장소도 렌더링 도구도 없고 스크립트도 실행할 수 없는 채팅
AI**라, 시스템 프롬프트에 그대로 붙여 넣고 **아래 목록(대상 물질 + 기본색)만 함께**
넘긴다. 규격은 발주가 바뀌어도 그대로이고, 바뀌는 건 아래 목록뿐이다.

결과물을 볼 수 없는 작업자를 위해 브리프는 **24×24 ASCII 격자를 먼저 그리고, 그걸
세어서 점검한 뒤 rect로 옮기는** 절차를 강제한다 — 줄 수·기본색 비중·최소 두께가 전부
글자를 세어 확인 가능해진다. 들어온 파일을 기계로 검수하는 스크립트는 발주자 쪽인
[`SKILL.md`](../.claude/skills/create-svg-assets/SKILL.md) §7.2에 있다.
