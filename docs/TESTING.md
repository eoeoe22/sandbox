# 검증 스크립트 (테스트)

이 문서는 저장소의 검증 스크립트 전문을 담는다. 각 절은 **무엇을 지키는가**와
**어떤 코드를 건드리면 이걸 돌려야 하는가**를 함께 적는다. 새 검증 스크립트를
추가하면 여기에 절을 하나 만들고, 제목은 **무엇을 지키는지 알 수 있는 설명적 이름**
(예: "소화 계통", "겹침(스며든 액체)")으로 쓴 뒤 절 본문 첫 줄에 `npm run ...`
스크립트 이름과 테스트 파일 경로를 적는다 — 목차 표가 그 둘을 이어 준다.

- `npm test` — 아래 목차의 `test:*` 전부 + 스냅샷 파일 + 열 커널 골든 테스트(열
  커널은 `wasm/` Rust 빌드 산출물이 있어야 하므로, 그게 없는 환경에선 개별
  스크립트로 돌릴 것).
- `npm run build` (따라서 `deploy`) — `check:material-ids` → `check:hand-icons` →
  `astro build` 순. **이 둘은 `npm test`에 안 들어 있고 빌드에 묶여 있어서**, 실패하면
  테스트가 아니라 배포가 멈춘다.

## 물질 id 중복 검사

`npm run check:material-ids` (내부적으로 `node scripts/check-material-ids.mjs` 실행).
`src/game/materials/`의 모든 `register({ ... })`에서 `id`를 정적으로 스캔해 중복이
있으면 목록을 출력하고 종료 코드 1로 실패한다. 중복이 없으면 통과.

이 검사는 `npm run build`(따라서 `deploy`)의 첫 단계로 묶여 있어, **Cloudflare Workers
빌드 시 자동 실행되며 물질 id가 겹치면 빌드가 강제 실패한다.** 새 물질을 추가할 때는
이 스크립트로 id 충돌 여부를 먼저 확인할 것.

## 전기(스파크) 패킹 검사

`npm run test:electricity` (`test/electricity.ts`). 스파크가 `aux` 16비트에 패킹하는
도체 클래스·펄스 강도가 서로를 침범하지 않는지 지킨다: 매체별 실측 도달거리(물·염수·
산·철), 등록된 전 도체의 클래스 왕복, 16비트 aux의 세이브/로드 왕복, `auxHi` 없는
구형 세이브 로드까지. 여기에 **전원 3종의 박자**도 같이 지킨다 — 배선 전용 터빈 출력,
태양광 패널의 배터리 박자, 그리고 **터빈이 리튬 배터리와 같은 주파수인지**(같은 기하의
실제 배터리와 맞춰 스파크가 뜬 **틱 번호 목록**을 비교하므로 위상까지 본다). 그중 핵심
회귀 핀은 **너울지는 증기**: 4틱 중 1틱만 증기를 넣어도 박자가 유지돼야 하고, 증기 틱
세기로 되돌리면 여기서만 1/4로 처진다(꾸준한 증기 장면은 옛 코드도 통과한다).

매체별 도달거리를 재는 첫 항목이 곧 **`Material.sparkLoss`** 검사이기도 하다 — 저항은
물질이 선언하고 `spark.ts`의 패킹 테이블은 거기서 파생되므로(예전엔 손으로 맞춰 둔 별도
배열이었다), 누가 물·염수·산의 저항을 건드리면 도달거리가 여기서 먼저 어긋난다.

**장치 쪽 계약**도 여기 있다. `directPulse`를 가진 **전기 카테고리 물질 전부**가 하네스에
등록돼 있는지 레지스트리에서 훑어 대조하므로(장치를 추가하고 검사를 빠뜨리면 그 자리에서
실패한다), 장치마다 400칸 몸체의 모서리 한 칸 접촉으로 전 칸이 그 틱에 켜지는지와, **세기
1**로도 결과가 완전히 동일한지를 본다.

**컨베이어**는 그 계약의 결과를 따로 잰다. **전원 게이트**: 188칸 벨트 한가운데의 모래 한
알이 전원 없이는 제자리이고(대조군 — 같은 장면에 배터리를 붙이면 간다), 왼쪽 벨트는 반대로
나르고, 배터리를 뽑으면 **한 카운트다운 안에** 멈추며, 벨트 전 구간의 카운트다운이 한
값이면서도 셀마다 자기 방향 비트를 유지한다. **계단 통전**: 계단식 벨트는 모서리로만
맞닿아 4방향 플러드로는 한 계단만 켜지므로, 발치의 배터리 하나가 **모든 벨트 셀을 손으로
강제 통전한 대조군과 정확히 같은 결과**를 내는지 본다(좌표를 박는 대신 대조군과 맞추는 것이
요점이다). **수송 깊이**: 40칸 사일로가 25칸 넘는 슬래브를 내보내면서도 **좁은 배출구는
여전히 유량을 조절**하는지, 그리고 벽에서 벽까지 꽉 찬 적재는 **한 칸도 안 움직이는지**
(비압축). **U자 벨트**: 골짜기에 부은 짐이 **바닥에 한 칸도 안 남고** 먼 턱을 넘어가는지 —
런을 하류부터 처리하지 않으면 오르막에서 한 칸짜리 층만 찔끔 넘어가며 여기서 깨진다.

전기 계통(`spark.ts`)이나 `Material.sparkLoss`, `Grid.aux`/저장 포맷,
`turbine.ts`/`solarpanel.ts`의 박자, `conveyor.ts`/`fan.ts` 같은 장치의 `aux` 패킹을
건드리면 이걸 돌릴 것.

## 나무 상자 오브젝트

`npm run test:woodbox` (`test/woodbox.ts`). 나무 상자의 회전·가연성·파괴 연쇄를
지킨다: 평지 밑변 flush 안착과 수직 낙하 시 각도 유지, **접촉 토크로 회전**(밀면 구르고
경사에서 굴러 내려감)과 **정지 시 90° 복귀**, **고속 충돌 파괴**(법선 접근 속도 기준 —
지면 고속 주행은 무사), 물 위 부유율, **액체·가루 진입 파티클**(착수/모래 충돌 시
1회성 산개, 가만히 얹으면 없음, 드럼통도 동일), 지속 가열 점화와 실제 Fire 방출, 다
타면 조각 3개(불 상속), 압사/폭발 직격도 같은 조각 3개, **파괴 원인별 산개 분기**
(충격 = 충돌·폭발·반물질일 때만 조각이 튀고 톱밥이 흩날림 / 연소·끼임·광선은 제자리에서
무너지고 톱밥도 그 자리에 쌓임), 조각 파괴 시 톱밥만 남고 추가 오브젝트 없음, 물 진화
후 생존, 용암은 (액체지만) 진화시키지 않음, **산 용해**(웅덩이에 닿으면 1초 만에 조각
3개 → 조각도 이어서 녹음, 조각 속도가 상자 속도와 정확히 일치해 안 튐 / 옆에 부은 얇은
산 막이 흘러와 닿기만 해도 파괴 + 톱밥 잔류 / **대조군 4종**: 같은 웅덩이의 물, 임계
미만 접촉 후 구출, 언 산, 같은 산 속의 드럼통·고무공).

오브젝트 레이어(`engine/objects.ts`)나 나무 상자 아트를 건드리면 이걸 돌릴 것.

## 드럼통 파괴 연쇄

`npm run test:drumbreak` (`test/drumbreak.ts`). 드럼통 3종이 나무 상자처럼 **조각 3개로
부서지는** 계통을 지킨다: 폭발 직격 시 통 → 조각 3개와 그때 한 번 쏟아지는 내용물(원유·
산, 빈 통은 0셀 대조군), 조각을 다시 부숴야 나오는 철가루와 **두 번 쏟지 않는 것**,
**갓 태어난 조각의 폭발 유예**(없으면 자기를 만든 플래시에 1틱 만에 삼켜져 기능이 안
보인다 — 유예가 끝난 뒤 새 장약에는 부서지는 것까지), **충돌로는 안 부서지는 것**(같은
낙하·같은 벽 충돌에서 나무 상자는 터지는 대조군과 나란히 — 폭발물에만 파괴), **2단 용융**
(1200°×24틱에 통이 열려 조각이 되고, 조각은 **더 높은** 1300°×8틱에 Molten Iron이 되며,
그 사이 1250°에서는 조각만 남는 갈림), 원인별 산개 분기(용융·압사는 제자리, 폭발은 튀고
각자 스핀), 조각이 고철 밀도라 **가라앉는 것**(통은 뜨는 대조군).

`breakDrum`·`DRUM_PIECE_*` 상수·`placeShard`나 드럼 조각 아트를 건드리면 이걸 돌릴 것.

## 쌓기 · 오브젝트끼리 충돌 파괴

`npm run test:stacking` (`test/stacking.ts`). 드럼통·나무 상자가 **둥근 사각형**으로
충돌하며 생긴 평면 위에 다른 바디가 실제로 쌓이는지, 그리고 속도로 부서지는 오브젝트가
**그리드가 아니라 다른 오브젝트에 부딪혔을 때도** 부서지는지를 지킨다: 상자 위 상자가
붙어 서서 완전 정지하는 것, 드럼통 3개가 기둥으로 쌓이는 것, 상자가 드럼통 뚜껑을 타는
것, **고무공은 여전히 공 위에서 굴러떨어지는 것**(원형 대조군), 아래 상자를 끌면 위
상자가 마찰로 실려 오는 것, 상자↔상자 충돌이 **양쪽 다** 터뜨리되 임계 아래면 아무것도
안 부수는 것, 화염병이 상자 위에 떨어져 깨지되 그 상자는 자기 임계에 한참 못 미쳐
멀쩡한 것, **드럼통 둘은 같은 속도로 들이받아도 멀쩡한 것**(강철은 폭발물에만 열린다는
대조군).

`bodyCore`·`gridContacts`·`resolvePair`·`solveNormalPair`·`CONTACT_ROUNDS`를 건드리면
이걸 돌릴 것.

## 화염병 오브젝트

`npm run test:molotov` (`test/molotov.ts`). 화염병의 **약한 파괴 임계**와 **심지 상태
기계**를 지킨다: 스프라이트 12×28 px에서 유도한 캡슐 6×14칸 일치, 바닥에 놓은 병은
넘어져도 생존하지만 **23칸 낙하는 깨짐**(같은 높이의 나무 상자는 무사 — "더 쉽게"의
대조군), **불붙은 파괴는 800°로 태어난 알콜이 실제로 타고** 꺼진 파괴는 20° 알콜에
Fire 0칸, **유리 조각은 `launchDebris`로 날아가고 알콜은 제자리에 남는 것**(파괴 그 틱에
유리 0칸 → 40틱 뒤 착지, 그리고 같은 파괴에서 유리 산개 폭 > 알콜 폭), **연못에 빠지면

## 염소 + 나트륨

`npm run test:chlorinesodium` (`test/chlorinesodium.ts`). 2Na + Cl₂ → 2NaCl, 즉 **불꽃 +

프로브다), **홀알갱이는 안 때리는 것**(바닥의 모래 한 칸이 제자리), 그리고 **고체 무영향이
완전한 것** — 맞닿은 유리가 안 깨지고(`DetonateOptions.shatters: false` — 진짜 폭발·우퍼는
기본값 true로 그대로 깬다), 충격파가 보통 실어 나르는 **`shockLoose` 고체(나노봇 프로브 —
염소가 안 죽이고 열사·충격사도 없는 유일한 물질)가 한 번도 사라지지 않으며**, 일반형으로
**날아다니는 Debris가 고체를 실어 나른 적이 없는 것**까지 훑는다.

여기에 **폭발이 아니라 연소라는 갈림**(같은 더미를 물에 담근 대조군은 Blast 발생 —
나중에 두 경로를 "정리"하려는 수정이 여기서 먼저 깨진다), 반응열이 **소금 융점 800°
아래**라 Molten Salt가 안 생기는 것, 그리고 같은 이웃 루프를 공유하는 **생물 살상 경로의
무회귀**.

`chlorine.ts`의 `updateChlorine`·`stirShock`이나 반응 온도 상수를 건드리면 이걸 돌릴 것.

## 염소 + 알루미늄

`npm run test:chlorinealuminum` (`test/chlorinealuminum.ts`). 2Al + 3Cl₂ → 2AlCl₃ —
게임 안에서는 **불꽃 + 흰 연기**이고 고체 생성물은 없다(염화알루미늄은 180°에서 승화하므로
연기가 곧 생성물이다). 나트륨 쪽과 나란히 읽으라고 만든 하네스다: 같은 기체, 같은 "밀폐
주머니 + 빈 주머니 대조군" 기하인데 **한쪽은 주울 수 있는 소금이 남고 한쪽은 아무것도 안
남는다.** 그래서 `SALT === 0` 검사가 여기 있다 — 두 반응을 "정리"하려는 수정이 여기서
먼저 깨진다.

못 박는 것:

- **공기도 불씨도 없는 밀폐 주머니에서 탄다**(염소 자체가 산화제다) + 같은 주머니를 비운
  대조군은 알갱이가 멀쩡하다.
- **1:1 소모는 주괴로 잰다.** 가루는 `combustion` 연료라 반응이 붙인 불이 이어서 더미를
  태우므로(그건 규칙이 새는 게 아니라 금속화재다 — 그쪽도 따로 못 박았다), 규칙 말고는
  아무것도 먹을 수 없는 **주조 막대**가 정량 장면이다: 기체 6칸 → 막대 소모 ≤ 6칸.
- **3형태의 서열**(활성 0.4 > 가루 0.2 > 주괴 0.06): 같은 장면·같은 시드로 **1틱**만
  돌려 잰다. 염소 이웃마다 굴리므로 구름 한가운데의 알갱이는 몇 틱이면 양쪽 다 끝나고,
  길게 돌리면 "둘 다 다 탔다"만 재게 된다.
- **주괴의 온도 게이트 양방향**: 상온 막대는 구름 속에서 그대로, 400°로 붙잡아 둔 같은
  막대는 타서 사라진다(그리고 **녹지 않는다** — Molten Aluminum 0칸).
- **공중에 뜬 가루는 분진 폭발**로 한꺼번에 간다(`tryDustExplosion`). 염소 전용 코드가
  아니라 "공기 없이도 붙는 불"이 기존 분진 규칙을 만나서 생기는 결과이고, 바닥에 깔린
  더미(위 항목)와 결과가 다르므로 따로 세워 둔다.
- 전 구간 **Blast 0칸** — 연소지 폭발이 아니다.
- **규칙 경합 — 행 순서가 사 주지 않는 것.** 염소와 반응하는 두 금속은 각자 더 느린
  구(舊)반응의 상대(활성 알루미늄↔물, 알루미늄 가루↔녹가루)와 **동시에** 닿아 있을 수
  있다. 그 행들이 염소 행보다 **앞에** 있지만, `tryReact`는 "상대를 찾고 확률까지 통과한
  첫 규칙"을 적용하므로 **앞선 행은 자기가 발동한 틱만 이기고, 여러 틱에 걸치면 큰 숫자가
  이긴다.** 실측(60회 독립 시행): 젖은 활성 알갱이 **물 30 / 염소 30**, 염소 대기 속
  테르밋 조합 **성사 23 / 먼저 탐 37**. 그래서 **비율이 아니라 "양쪽 다 실제로 일어난다"**
  를 못 박는다 — 비율 단정은 과적합이고(알갱이가 어느 쪽 이웃을 몇 개 끼고 있느냐로
  흔들린다), 한쪽이 **0으로 굶은 것**은 어느 방향이든 진짜 회귀다(염소 확률을 올려 웅덩이가
  영영 안 끓거나, 내려서 구름이 젖은 알갱이를 영영 못 먹거나). 각 장면은 한 번 결판나는
  경주라 긴 한 판이 아니라 **짧은 독립 시행 여러 판**으로 돈다.

연기 검사만 `setSmokeLevel('high')`로 돈다: 반응 연기는 기본값 `medium`에서 35%로
솎이므로(SimContext `applySmokeLevel` — 이 반응과 무관한 전역 가독성 손잡이) 세 칸짜리
장면에서는 시드 뽑기가 되어 버린다.

`chlorine.ts`의 `chlorineMetalBurn`이나 세 알루미늄 파일의 `CHLORINE_REACT_*` 상수를
건드리면 이걸 돌릴 것.

## 가용성(섞이는 액체)

`npm run test:miscible` (`test/miscible.ts`). `Material.miscible` — **밀도 분리를 끄는
쪽**(`SimContext.tryMove`)과 **상호확산**(`behaviors.diffuseMiscible`) 두 반쪽이 함께
있어야 "섞인다"가 되는 태그다. 한쪽만 있으면 각각 다른 방식으로 망가지고(확산만 있으면
다음 틱에 밀도가 도로 밀어 올리고, 차단만 있으면 서로 통과도 못 하는 두 층이 된다),
그 둘을 갈라서 재기 어렵기 때문에 장면 기하가 이 하네스의 핵심이다.

**빈칸이 하나도 없는 밀폐 상자**에 두 액체를 반씩 채운다. 흐를 곳이 없으므로 셀을 움직일
수 있는 것은 밀도 스왑 아니면 가용성 확산뿐이고, 결과는 그 쌍에 대한 이야기가 된다.
점수는 `crossed` — 부은 층의 몇 %가 **반대쪽 절반**으로 넘어갔는가. 완전 균질이 50%,
안 섞이면 0%, 그리고 **떠올라 층이 뒤집힌 경우는 100%**다. 이 마지막 값 덕분에 두 기준선
(`MIXED_BAR` 0.25 / `SEPARATED_BAR` 0.85)이 멀찍이 떨어져 있어도 둘 다 날카롭다.

- **알콜 ↔ 물**: 알콜을 **아래에** 부어도(밀도대로면 통째로 떠올라야 하는 배치) 기둥
  전체로 퍼지고, 위에 부어도 가라앉는다. 대조군은 **가솔린**(같은 밀도 관계, 태그 없음 →
  100% 떠오름).
- **한 번 섞이면 안 갈라진다**: 체커보드로 미리 저어 둔 용액을 900틱 방치해도 층이 안
  생긴다(태그의 `tryMove` 반쪽이 존재하는 이유).
- **비눗물 ↔ 기름 4종**(원유·휘발유·등유·경유)은 유화되고, **같은 기름 + 맹물** 짝은
  층으로 남는다. 물질 변화는 없다(기름 칸 수 보존).
- **비눗물 ↔ 물**, **셀 수 보존**(섞임은 스왑이다), **얼면 안 움직인다**(-120°로 붙잡은
  알콜 기둥이 옆 물로 한 칸도 안 샌다), **모래는 여전히 가라앉는다**(tryMove 변경이 낙하
  경로 전체에 얹혀 있으므로 필요한 대조군), **알콜은 여전히 가솔린 위에 뜬다**(태그는
  전역 스위치가 아니라 쌍별 면제다).

`diffuseMiscible`은 **이웃에 상대가 있을 때만 RNG를 만진다.** 순서를 뒤집어(먼저 굴리고
나서 찾기) 두면 물 한 칸 한 칸이 매 틱 난수를 뽑아 공용 스트림의 위상이 밀리고, 이
계통과 무관한 시드 고정 하네스가 깨진다 — 실제로 `test:extinguish`의 석탄 진화 장면이
55/55에서 10/55로 뒤집혔다. 성능이 아니라 **결정성** 때문에 그 순서다.

`Material.miscible` 쌍을 추가하거나 `MISCIBLE_DIFFUSE_CHANCE`·`tryMove`의 밀도 분기를
건드리면 이걸 돌릴 것.


## 산성 슬라임 레시피

`npm run test:acidslime` (`test/acidslime.ts`). **산 + 슬라임 → 산성 슬라임**과 그 되돌리기
(**물 + 산성 슬라임 침식 → 일반 슬라임**) 양방향을 지킨다. 두 방향 모두 **소모 계산이
틀리면 조용히 망가지는** 종류다 — 시약을 안 없애면 한 방울이 세상을 다 바꾸는 촉매가 되고,
너무 많이 없애면 아예 발동한 적이 없는 것처럼 보인다. 그래서 결과만큼 **장부**를 센다.

`test:miscible`과 같은 **빈칸 없는 밀폐 상자**를 쓴다(산이 더 가벼워 위에 깔리고, 둘은 한
면으로 만난다). 600틱.

- **레시피**: 경계가 산성 슬라임으로 바뀌고(blob의 40% 이상), **소모된 산 < 전환된
  슬라임**(한 번 물어뜯고 끝나지 않는다), **그러나 0은 아니다**(공짜 촉매가 아니다),
  **goo 총량 보존**(Slime + Acid Slime = 처음 슬라임 수). 넷이 같이 맞아야 통과다 —
  두 실패 모드가 서로 반대라서다. 안 소모되면 한 방울이 세상을 다 바꾸고, 매번 소모되면
  (처음 구현이 그랬다) 효과로 안 읽힐 만큼 굼뜨다.
- **대조군(슬라임 없는 산)**: 같은 상자에 물을 깔면 산은 **한 칸도** 줄지 않는다 — 위
  1:1 계산이 "다른 경로가 산을 먹었을 뿐"이 아님을 못박는다. 산성 슬라임도 0이다.
- **되돌리기**: 물속 blob은 **계속 먹으며 커지지만**, 끝난 뒤 goo의 산성 **비율**이 15%
  아래로 떨어지고(실측 6%) 물은 소모된다. 카운트가 아니라 비율로 재는 건 이 장면이 침식에
  가장 불리한 기하이기 때문이다 — 꽉 찬 정사각 blob은 겉면만 젖고, 거기서 자란 일반
  Slime이 중심부를 감싼다(자세히는 [MATERIAL-SYSTEMS.md](./MATERIAL-SYSTEMS.md)의
  "산 ↔ 물로 오가는 슬라임").
- **대조군(물속의 일반 슬라임)**: 산성 슬라임이 **0**이다. 산 말고는 산성 슬라임을 만드는
  경로가 없다는 것 — 레시피가 유일한 공급원이라는 뜻이다.
- **같은 틱에 되돌아가지 않는다**(확률·기하 아닌 **스캔 순서** 검사): 바닥에 산성 슬라임,
  그 위에 물, 대각선에 산을 놓고 모든 확률을 강제로 성공시켜 **1틱**만 돌린다. 씻긴 칸이
  `markMoved`를 빠뜨리면 아직 차례가 안 온 산이 그 칸을 반응 상대로 집어 곧바로 산성으로
  되돌리고, 물과 산만 사라진 채 **되돌리기 기능 자체가 조용히 무효화된다**. 실제로 그 한
  줄을 빼면 이 검사가 빨개진다.
- **스파크가 슬라임으로 돌아오는 자리도 같다**: `packSpark`/`conductorClass`로 세기 1짜리
  슬라임 스파크 한 칸을 직접 만들고(세기 1이라 옆 산으로 펄스가 넘어가지 않는다) 대각선에
  산을 둔 뒤 1틱. `spark.ts`의 복귀 지점이 표시를 빠뜨리면 **Spark → Slime → Acid Slime**
  가 한 틱 안에 이어진다 — `reactions.ts`가 금지하는 같은 틱 연쇄다. 이 역시 해당 줄을
  빼면 빨개진다. **레시피 하나가 어떤 물질을 반응 표의 상대로 만들면, 그 물질을 맨
  `set()`으로 쓰는 모든 자리가 새로 위험해진다**는 게 이 두 검사의 요지다.

## goo 진공 기포

`npm run test:goovoids` (`test/goovoids.ts`). **흐름 게이트 + `viscosity`를 둘 다 가진 goo
셋**(Slime·Acid Slime·Honey)이 가라앉으면서 **갇힌 빈칸을 안고 굳지 않는지**를 지킨다. 빈칸은
배경색(검정)으로 그려지므로, 이건 성능이 아니라 **보이는 것**에 대한 검사다(→
[PHYSICS.md](./PHYSICS.md)의 "goo 안의 검은 구멍").

12×12 blob을 공중에서 떨어뜨려 400틱 동안 **매 틱** "3면 이상이 goo인 빈칸" 수를 세고 그
평균을 본다. 마지막 상태가 아니라 평균인 이유는 이 현상이 **가라앉는 동안의 정상 상태**이기
때문이다 — 다 굳고 나면 사라지지만 눈에 보이는 건 그 과정이다.

- **goo 셋의 평균이 6 미만**. 수정 전 슬라임 14.9·산성 슬라임 15.2·꿀 13.7(최대 40대),
  수정 후 3 근처다.
- **경계 모드를 구분한다**: 맵 가장자리에 기댄 구멍은 `borderMode: 'wall'`에서는 갇힌
  기포지만 `'void'`에서는 셀이 실제로 떨어져 나가는 열린 가장자리다. 같은 장면을 두 모드로
  돌리되 **모든 확률을 강제로 실패**시켜, 게이트 없는 함몰 보정만이 셀을 움직일 수 있게
  만든다 — 'wall'에서는 내려앉고 'void'에서는 그대로 있어야 한다.
- **언 goo는 안 움직인다**: 밀폐된 한 칸 주머니 위에 −50°로 얼린 꿀을 놓고 20틱. 함몰
  보정은 게이트보다 앞서 돌고 `SimContext.tryMove`의 빈칸 이동은 스스로 동결을 보지 않으므로,
  헬퍼가 직접 막지 않으면 **굳은 꿀이 주머니로 흘러내린다**(`freeze`가 하지 않겠다고 약속한
  바로 그 일). 가드를 빼면 이 검사가 빨개진다.
- **대조군 둘**: Lava(게이트만)와 Mud(태그만)는 원래 멀쩡했고 지금도 멀쩡하다. 이 둘이
  붙어 있어야 "둘 다 있어야 생긴다"는 진단이 유지된다.
- **그럼에도 여전히 goo다**: 40칸 자유낙하가 물의 2배를 넘고(슬라임 174틱 vs 물 34틱),
  퍼짐 폭이 물의 75% 미만이다(15열 vs 36열). 구멍을 없애자고 goo를 묽게 만들면 여기서
  걸린다.

## 액체 금속 유동성

`npm run test:liquidmetalflow` (`test/liquidmetalflow.ts`). **금속 melt에는 점성 장치가
없고, 비금속 melt에는 있다**를 양쪽에서 지킨다(→ [PHYSICS.md](./PHYSICS.md)의 "액체 금속
점성 제거"). 실수로 되돌리기 쉬운 종류의 규칙이라("느낌상" 게이트를 다시 달거나, 새 melt를
용암 블록에서 복사해 `viscosity`를 물려받거나) 다른 테스트가 절대 못 잡는다.

40칸 바닥 한가운데에 **4×12 기둥**을 세우고 45틱 뒤 puddle이 덮은 **열 수**를 센다(40이면
벽에서 벽까지 완전 평탄).

- **Molten Iron·Molten Aluminum·Molten Iron Ore·Molten U238**은 물(대조군)과 같은 대역
  (27~30열)에 들어온다. 각 장면은 **melt 칸 수가 그대로인지**도 같이 확인한다 — 굳어 버린
  기둥의 정지를 "안 퍼졌다"로 오독하지 않기 위해서다.
- **Lava·Molten Glass·Molten Salt·Slag**는 같은 창에서 12~19열에 머문다.
- **선언 검사**: 액체 금속 명단 중 `viscosity`를 단 물질이 있으면 이름을 찍고 실패한다.

측정 창이 45틱으로 짧은 건 의도다. 게이트는 **느리게 할 뿐 멈추지 않으므로** 길게 두면
용암도 평탄해져 두 무리가 구분되지 않는다.

## 반물질 전면 소멸

`npm run test:antimatter` (`test/antimatter.ts`). 반물질이 **Wall·Void를 뺀 모든 물질을
지우는 것**을 지킨다. 핵심은 **레지스트리 훑기**다 — 등록된 전 물질을 그레인 옆에 세워
보고 살아남는 게 있으면 **그 이름을 출력하며 실패**하므로, 나중에 누가 조용히 면제
조건(방폭·무적·기체 따위)을 되살리면 이 검사가 먼저 깨진다.

나머지는 예외 둘과 섬광 표식이다: Wall·Void 생존과 **Void가 오히려 그레인을 삼키는
대조군**, 기체(Steam)의 1:1 소멸과 1200° 섬광, **표식 붙은 Fire/Smoke는 건너뛰고 평범한
Fire/Smoke는 소멸시키는 짝 장면**(같은 기하, 차이는 `aux` 표식 하나뿐), 실제 틱 루프에서
Diamond·Clone이 갉여 나가는 장면, 그리고 자기잠식 방지의 못인 **효율 장면**(밀폐
통로에서 그레인 36개 → 소모 그레인 수 ≈ 파괴 칸 수, 기준 0.9배 — 표식이 사라지면 이
비율이 먼저 무너진다).

`antimatter.ts`의 이웃 판정이나 `FLASH_MARK`을 건드리면 이걸 돌릴 것.

## 겹침(스며든 액체)

`npm run test:overlap` (`test/overlap.ts`). 가루 속에 스며든 액체가 **지워지지 않고**,
**상호작용도 한다**는 두 가지를 지킨다.

충격파 쪽: 젖은 모래를 약한 폭발로 밀어내도 물 총량이 그대로고(파편이 겹침을 업고 난다 —
`Material.overlapCarrier`), 착지 후에도 젖은 채로 남으며, 강한 폭발로 부수면 그 자리에서
**수증기**가 난다(마른 모래 대조군은 0칸). 그리고 **파괴력 0인 우퍼 충격파는 젖은
모래에서 아무것도 만들지 않는다** — 수증기·유리·깨진 유리 0칸, 실제 셀 최고 온도 ≤ 25°,
물 총량 완전 보존. 이 셋이 한 버그의 세 얼굴이다: 파편은 `temp`에 **비행 상태**를
싣는데(`packedTemp`) 업고 있던 물방울이 혼자 빠져나오면서 그 값을 "공유하던 온도"로 들고
나와 3만 도로 표면화했고, 그 물이 수증기가 되고 옆 모래가 유리로 구워졌다. 그래서
**캐리어의 승객은 화물** — 반응도 이동도 하지 않고 착지할 때만 세상에 돌아온다.

상호작용 쪽 장면은 전부 **벽으로 밀폐한 데다 빈틈 없이 꽉 채운 주머니**다 — 알갱이가
떨어질 틈도, 스며든 액체가 표면화할 빈칸도 없어야 "안에서 물었다"가 "새어 나와 물었다"로
오독되지 않는다(처음 쓴 판은 벽과 더미 사이에 1칸이 떠 있어서 고치기 전에도 통과했다).
그 주머니에서 스며든 산이 모래를 녹이고(깨진 유리 대조군은 무사), 철가루에선 수소가 나고,
**산성 증기가 자기가 들어앉은 체를 녹이고**(기체는 가루가 아니라 다공체에 스민다 —
대조군은 같은 체에 **무해한 기체**를 채운 장면이다. 예전엔 내산 다공체인 Pump가 대조군을
맡았는데, 전기 카테고리의 내산성이 태양광 패널만 남고 걷히면서 다공체가 전부 녹게 됐다), **1차 셀 물이 0칸인데도** 활성 알루미늄이 수소를 내고, 스며든 액체
갈륨이 알루미늄 가루를 활성화하되 자기는 안 줄고, 스며든 과산화수소가 효모에 분해돼
물이 된다(선언형 반응 테이블이 **양방향**으로 물린다 — 호스트 쪽 표와 유체 쪽 표가 서로
다른 코드 경로라 장면도 따로 있다), 시멘트가 스며든 물로 굳는다. 무회귀 핀 둘: **ANFO**
(질산암모늄에 스민 경유는 반응 상대가 없으니 그대로 남아야 한다)와 **배수**(상호작용
패스가 이동 턴을 잡아먹지 않는다). 모든 장면이 (host, overlay) 불변식을 함께 훑는다.

마지막 장면은 **겹침이 알갱이를 따라가지 *않아야* 하는 자리**를 반대로 못 박는다: 뜬 가루
컬럼에서 겹침은 알갱이의 성질이 아니라 **흘수선**이라, `shiftPowderColumnUp/Down`은 일부러
겹침을 제자리에 두어 잠긴 칸 수가 알갱이가 아니라 **수면에 고정**되게 한다. 부력 루프를
거치지 않고 두 시프트를 **직접 호출**해서 본다(부력 루프는 한 틱에 수십 번 부르므로 한
번의 시프트가 무엇을 했는지 안 보인다). "일관성" 삼아 겹침까지 같이 복사하면 잠긴 칸 수가
시프트에 반응하지 않게 되고 끝 칸의 물방울이 **복제**되는데, 두 증상이 여기서 먼저
깨진다. 짝 장면 하나는 **반례**다 — 완전히 잠긴 채 하는 시프트는 앞면이 삼킨 만큼 뒷면이
내놓아 잠긴 칸 수가 그대로다. 불변식은 "시프트당 ±1"이 아니라 그 고정과 질량 보존이라는
뜻이니, 여기에 ±1 단언을 넣지 말 것.

`SimContext`의 겹침 판정·`shiftPowderColumnUp/Down`·`reactions.ts`의 `tryReactSoaked`·
`corrosion.ts`의 `tryCorrodeSoaked`·`blast.ts`의 `resolveSoaked`를 건드리면 이걸 돌릴 것.

## 시작 화면 세계

`npm run test:startscreen` (`test/startscreen.ts`). 루트(`/`) 배경에서 도는 경량
엔진(`src/game/startScreen.ts`)을 캔버스 없이 돌린다. 컴포넌트는 캔버스와 RAF만 맡으므로,
실제로 틀릴 수 있는 것은 전부 여기 있다: **설정 UI가 없어서 못 박아 둔 세 값**(속도 ×1의
스텝 간격·벽/바닥·연기 중간 — 엔진 기본값이 흘러가도 시작 화면은 안 흔들려야 한다),
**경량 로드**(등록 물질 수가 전체 팔레트 미만 — 누가 전체 배럴로 되돌리면 여기서 먼저
깨진다. **소금은 여기서 갈린다**: Fire → Salt Water → Salt 사슬이라 모듈은 못 빼므로
검사도 "안 실린다"가 아니라 **"돌려 봐도 한 칸도 안 생긴다"** 를 지킨다 — 반응 로직이
실제로 안 도는 조건이 그쪽이다), **떨어지는 줄**(다 떨어지는지, 각자 자기 열에 머무는지,
**빈 화면에서 시작하는지**, 그리고 **천장에서 아래로** 떨어지는지 — 이 자리를 위아래로
뒤집어 놓았던 옛 랜딩 페이지가 있었다), **벽/바닥**(가로로 꽉 찬 막대를 떨어뜨려도 한
알갱이도 안 새고 바닥에 쌓인다), **배수**(꽉 찬 세계가 다시 빠져 굳지 않는다 — 안 그러면
벽 때문에 시작 화면이 멎는다), **1초 박자**(초마다 정확히 1회 — 매 틱도 아니고 한 번뿐도
아니다. 자리는 매번 새로 뽑는다), **룰렛의 셔플백 규칙**(후보가 불·충격파 둘뿐이라
사실상 번갈아 나오기로 굳는데, 그게 "한 바퀴 전엔 재등장 없음"의 2종짜리 모습이다),
**터지는 자리**(고른 열의 더미 표면을 찾아 원이 거기 **걸터앉는지** — 절반은 공중, 절반은
더미 속. 아직 안 쌓인 열이면 아래쪽 허공), 그리고 **무엇이 실제로 나오는가**(불은 자기
초기 온도로 뜨겁게 태어나 **밑에 깔린 휘발유에 실제로 옮겨붙고**, 충격파는 진짜 Woofer
파동을 띄워 가루를 밀되 **물질을 지우지 않는다** — 이 확인은 날아간 파편이 다시 내려앉을
때까지 기다려야 한다. 비행 중에는 Sand가 아니라 Debris로 읽힌다).

**클릭 충격파**(`burstAt`)는 따로 두 절이다. 첫째, **누른 칸 그 자리에서** 터지고(자동
이벤트처럼 자리를 새로 뽑지 않는다), 진짜 파면을 띄워 가루를 밀되 물질을 지우지 않으며,
**화면 밖 좌표는 조용히 무시한다** — 격자가 캔버스 안에 가운데 정렬돼 있어 레터박스 여백을
누르면 실제로 밖이 나온다. `motion: false`(움직임 최소화)에서도 터지는 것을 같은 절에서
잰다: 그 스위치가 끄는 것은 **사용자가 일으키지 않은** 움직임뿐이다. 둘째, **박자를 흔들지
않는다** — 매 틱 눌러 대도 자동 이벤트는 여전히 1초에 한 번이고, 그동안의 클릭은
`burstCount`에 따로 쌓인다(`eventCount`는 1초 박자를 재는 값이라 섞이면 뜻이 흐려진다).

**불 검사는 자리 검사의 근거**이기도 하다: 원을 표면 한 칸 **위**에 얹으면 불은 기체라
붙기 전에 떠올라, 같은 장면에서 휘발유가 한 칸도 안 타고 35틱 만에 다 꺼진다. "깔끔하게
얹기"로 되돌리려는 수정이 여기서 먼저 깨진다.

`startScreen.ts`의 스트림·배수·이벤트·룰렛·클릭 충격파·해상도나 `materials/lite.ts`를
건드리면 이걸 돌릴 것. **시작 화면의 포인터 배선**(`.foreground`/`.item`/`.stage`의
`pointer-events`)은 CSS라 여기서 안 잡힌다 — 그건 브라우저에서 눌러 봐야 한다(메뉴 버튼
세 줄이 눌리는가 / 그 밖의 아무 데나 눌렀을 때 충격파가 터지는가).

## 기어다니는 벌레(흰개미·나노봇)

`npm run test:crawler` (`test/crawler.ts`). 두 벌레가 `crawler.ts` 하나를 공유하면서
갈라지는 지점을 지킨다.

흰개미는 **먹은 것의 절반만 번식**하는 것을 **비율로** 잰다 — 밀폐된 통나무 더미에서
*먹은 칸 수*와 *늘어난 개체 수*를 같이 세고 후자가 전자의 40~60%인지 본다(옛 100%
증식이면 둘이 **같아지므로** 이 비율이 곧 회귀 핀이다). 나머지 반쪽으로 "군집은 여전히
번식한다"와 "죽은 개체가 없어 톱밥도 0칸"(= 줄어든 나무가 다른 물질로 둔갑한 게 아니다)이
같은 장면에 붙어 있다.

나노봇 쪽은 **금속 기억** 전체다: 먹이 블록 한가운데 가둔 개체가 무리 전체를 같은 기억으로
물들이는 것(철 대조군 포함), **200틱을 기어다녀도 기억이 안 깨지는 것**(방향이 매 틱 같은
aux 워드의 하위 3비트를 덮어쓴다 — 비트 배치가 어긋나면 여기서 먼저 깨진다), 그리고 기억을
따르는 세 형질 — 660°에 녹는 알루미늄 몸과 **같은 700° 열판 위에서 멀쩡한 철 몸**(대조군)·
1250°의 철 몸 → Molten Iron·600° 무사, 폭심(`blastDeathIdFor`)과 인접 섬광(`touchingBlast`)
**양쪽 경로**에서 나오는 자기 금속 가루와 **다른 금속 가루 0칸**, 소금물 탱크에서 녹스는
철 몸과 안 녹스는 알루미늄 몸. 인접 섬광 장면은 `flashCell()`로 진짜 섬광을 찍어야 한다 —
손으로 놓은 Blast 셀은 상온이라 **브러시 시드로 읽혀 크레이터를 터뜨리고**, 그러면 가장자리
경로 대신 폭심 경로를 다시 재는 데다 잔재까지 그 크레이터에 묻힌다.

`crawler.ts`(aux 비트 배치·`eatAndReproduce`)나 `termite.ts`/`nanobot.ts`, `blast.ts`의
잔재 경로를 건드리면 이걸 돌릴 것.

## 소화 계통

`npm run test:extinguish` (`test/extinguish.ts`). "물을 부어도 증발만 빠르고 안 꺼진다"를
고친 라운드를 지킨다. 원인 넷을 각각 못 박는다: **불꽃 하나가 물 한 칸만 쓰는 것**(개편
전엔 인접한 물을 8칸까지 전부 증기로 바꿨다 — 타는 더미는 불꽃을 공짜로 재생산하므로 이길
수 없는 교환비였다), **표면만 식힌 석탄이 4틱 만에 자기 심부 전도열로 되살아나는 것**
(심부까지 흘려 넣는 `chillThroughFuel` 플러드가 필요한 이유 자체의 계측), 소화 중인 물이
**안 끓는 것**, 밀폐된 물이 **증기 나갈 자리 없이는 안 끓는 것**. 그리고 물이 나무·석탄
더미를 실제로 끄고 **연료를 남기는 것** — 아무것도 안 부은 대조군은 다 타 없어지므로
"꺼졌다"가 "다 탔다"로 오독되지 않는다.

**화재 등급 갈림에는 전부 같은 기하의 짝 장면**이 붙어 있다: 유류는 안 꺼지고 CO₂는 꺼지는
짝, 타는 알루미늄 알갱이는 물 한 틱에 안 꺼지는데 **같은 물에 같은 기하의 석탄 알갱이는
꺼지는 짝**(차이는 `fireClass` 태그 하나뿐)에 수소는 계속 나오는 것, 소화 중인 물이 안
끓는데 **같은 기하의 뜨거운 돌판 위에서는 끓는 짝**, 뚜껑을 열면 끓는 짝, Snow/Ice가 불을
끄고 **증기가 아니라 물을 남기는 것**, CO₂만 소모되지 않는 것.

여기에 **`SimContext.fireActive` 전용 장면**이 붙어 있다 — `fightingFire`의 7×7 훑기를 끄는
O(1) 게이트라(증기 설비처럼 저수조를 계속 끓여 두는 장면에서 틱의 27%였다) 조용히 반대로
굳으면 켜진 채면 차폐가 안 풀리고 꺼진 채면 개편 전체가 무효가 된다: 불이 타는 동안 서고,
꺼지면 내려가고, 그러면 물이 다시 끓고, 불이 없던 세계에선 한 번도 안 서는 것.

마지막은 **레지스트리 훑기**다 — 산+금속 명단 검사와 같은 발상으로 전
`Material.combustion` 연료의 화재 등급 **그리고 `burnChance`·발화점**을 명단과 대조하고
어긋나면 **새 명단을 출력하며 실패**하므로, 새 금속·유류 연료를 등급 없이 추가하거나 연소
경제를 재조정하면 이게 먼저 깨진다. 제원까지 볼 수 있는 건 그게 `Material`에 실려 있기
때문이다(옛날엔 각 연료 모듈 안 `const SPEC`이라 그 연료 말고는 아무도 못 읽었다).

`suppress.ts`·`Material.fireClass`/`douses`·`Material.combustion`·`fire.ts`의 소화 루프·
`combustion.ts`의 물 접촉·물/눈/얼음의 비등 판정을 건드리면 이걸 돌릴 것.

## 상전이(녹는점·어는점)

`npm run test:phasechange` (`test/phasechange.ts`). "임계 온도 하나 → 다른 물질" 꼴의
전이를 선언(`Material.phaseChange`)으로 옮기고 공용 패스 `materials/phasechange.ts`가
적용하는 계통을 지킨다. 장면을 손으로 고르지 않고 **레지스트리를 훑으므로**, 새 상전이
쌍은 선언만 하면 검사에 자동으로 들어온다: 전 선언의 `at`·`into`가 실제로 해석되는지,
임계를 넘기면 **진짜로 바뀌는지**(선언해 놓고 `tryPhaseChange` 호출을 잊으면 여기서
깨진다), 임계 **직전**에는 안 바뀌는지, 쌍의 두 점이 떨어져 있어 되튀지 않는지
(히스테리시스).

`at`·`into`가 둘 다 thunk인 이유가 곧 첫 검사의 이유다 — 용융쌍은 서로를 import 하므로
(glass ↔ molten glass, iron ↔ molten iron, ice ↔ water) `register` 리터럴이 모듈 로드
중에 상대 값을 읽으면 `undefined`가 되는데, 이건 예외로 죽는 게 아니라 **`t < undefined
=== false`로 판정이 뒤집혀 상온에서 전부 녹는** 조용한 고장이다(실제로 철·유리·깨진
유리·얼음 4종이 그랬다).

마지막은 **호출 위치**를 못 박는 장면이다 — 이 패스가 엔진 구동이 아니라 각 `update`에서
불리는 건 물에 닿은 용암이 자기 응고점보다 담금질을 먼저 답해야 하기 때문이라, 응고점에
있는 용암이 물 밑에서 흑요석이 되는 것과 물을 뺀 같은 기하가 Stone이 되는 대조군이 나란히
서 있다.

`phasechange.ts`·`Material.phaseChange` 선언이나 전이를 가진 물질의 `update` 순서를
건드리면 이걸 돌릴 것.

## 물질 도감 커버리지

`npm run test:codex` (`test/codex.ts`). `/guide` 도감 페이지가 레지스트리에서 **빌드
타임에** 뽑히는 산출물이라는 것을 지킨다. 도감의 고장은 크래시가 아니라 **구멍**이라
(설명이 없는 물질, 아무 카드도 설명하지 않는 태그, 페이지가 부르는데 아무도 안 적은
용어 — 전부 아무것도 안 터뜨린다) 검사는 전부 장면이 아니라 훑기다.

핵심은 **필드 커버리지**다 — 어떤 물질이든 실제로 세팅한 모든 `Material` 필드를 모아,
수치 표(`codex/stats.ts`)·특성 카드(`codex/traits.ts`)·**의도적 제외 목록**
(`codex/fields.ts`) 중 하나에 반드시 속하는지 보고 아니면 **그 이름을 출력하며
실패**한다. 그래서 엔진에 태그를 추가하고 도감을 잊을 수가 없다. 구조체는 점 표기로
부분을 주장하고 훑기도 부분 단위로 내려가므로 나중의 `thermal.capacity`가 고아로 잡힌다.
그게 관행이 아니라 강제라는 걸 짝 검사가 지킨다 — **도감이 보여 주는 구조체를 통째로만
주장하면** 그 이름을 대며 실패한다(통째 주장이야말로 새 부분이 조용히 새어 들어오는
모양이다). 제외 목록의 구조체만 면제다.

나머지는 팔레트 명단 = 도감 명단, 설명문의 **양방향** 대조(빠진 물질 / 남은 설명)와 두
로케일 각각, 태그 용어의 같은 대조에 **미사용 용어 검사**(아무도 안 부르는 용어는
커버리지처럼 보이면서 아무것도 설명하지 않는다), 세 절(수치·특성·반응)이 전부 비어 있지
않은지, 모든 `refId`가 실재하는 물질인지, 아이콘 스프라이트에 빈 심볼이 없는지, 그리고
**JSON 왕복** — 추출물에 함수가 섞이면 아일랜드 props 직렬화가 깨지므로, 무엇이
잘못됐는지 여기서 먼저 말해 준다.

태그 이름·설명은 `i18n/codexTerms.ts` **한 파일**에 태그별로 두 언어가 나란히 있어서,
한쪽 언어만 적으면 검사가 아니라 **컴파일이 막는다**(`Record<Locale, CodexTerm>`).

여기에 훑기가 아닌 항목이 하나 붙어 있다 — **번들 경계**다. 러너(`test/run-codex.mjs`)가
esbuild `metafile`로 `src/i18n/index.ts`의 import 그래프를 훑어, 도감 텍스트 표가 거기
닿아 있으면 실패한다. 그 배럴은 모든 아일랜드가 `t()`를 가져가는 곳이라 거기 닿은 것은
아일랜드끼리 공유하는 청크로 들어가고, 실제로 **샌드박스와 시작 화면이 이중 언어
백과사전을 내려받고 있었다**(공유 청크 71.5KB → 31.4KB). 자세한 것은
[`CODEX.md`](./CODEX.md).

`codex/`의 스펙 목록·`i18n/codex.*.ts`·`i18n/codexTerms.ts`·`i18n/index.ts`의 import·
`Material`에 새 태그를 건드리면 이걸 돌릴 것.

## 활성 타일 스캔 동등성

`npm run test:active-tiles` (기존). 활성 타일 CA 스캔이 전면 스캔과 비트 동일한지(매 틱
동일, 결정론) 확인한다. 설계와 실측은 [`PERFORMANCE.md`](./PERFORMANCE.md) §4 참고.

무작위 채움 장면들에 더해 **표적 장면**이 몇 개 붙어 있고(뜬 가루 뗏목, 갇힌 플럭스,
섞인 부유 가루…), 그중 하나가 **전원이 들어온 U자 컨베이어**다. 무작위 장면은 등록된 모든
id를 뿌리므로 컨베이어 셀도 들어가지만 **전원이 없어** 업데이트 첫 줄에서 반환한다 — 즉
벨트 로직은 한 줄도 안 돌았다. 컨베이어는 **격자 스캔 순서대로 풀리지 않는 유일한 물질**
(런을 하류부터 스스로 걷는다)이라, 스캔이 아직 안 닿은 셀에 쓰고 이미 닿은 셀에 스탬프를
찍는다 — 타일 스캔이 건너뛸 타일에 일을 남기기 딱 좋은 모양이라 표적 장면이 필요했다.
장면에는 **"짐을 실제로 실어 올렸는가"** 검사가 붙어 있다. 처음 쓴 판은 "아무 셀이나
바뀌었는가"였는데, 부은 모래는 벨트가 서 있어도 중력으로 주저앉으므로 **배터리를 지워도
통과했다** — 지금은 부은 높이보다 위, 먼 팔 위쪽에 모래가 올라왔는지를 보고, 배터리를
지우면 실제로 실패한다(확인 완료).
